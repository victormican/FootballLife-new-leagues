# Mapa del ejecutable de FL 2026 (2026-11-06)

Primero el mapa, luego los parches. Este documento es el punto de partida para entender el
`FL_2026.exe` sin volver a hacer arqueología a ciegas, y para escalar el trabajo de ligas,
copas y Select Team.

## 1. El fichero

| dato | valor |
|---|---|
| tamaño | 458 MB (la mayor parte es `.impdata`, datos empaquetados) |
| secciones | 19 |
| código | `.trace`, 39.0 MB (`va 0x140001000`, `raw 0x600`) |
| funciones delimitadas | **158.648** (`.pdata`, 12 B por entrada) |
| imports | **837** (IAT resuelta) |
| base / ASLR | `0x140000000`, **sin ASLR** |
| mapa VA → fichero | `VA = offset + 0x140000a00` (comprobado con bytes conocidos) |

Secciones: `.trace` (código), `.rdata`, `.data`, `.pdata`, `.xtext`, `.tls`, `.bss`, `.data1`,
`.impdata` (los datos del juego), `.reloc`, `.xcode`, `.rsrc`, `.text1`, `.xtls`, `.idata`,
`.sxdata`, `.sbss`, `.tls$`, `.edata`.

## 2. Herramienta: índice navegable

`tools/fl26dis.py` recorre el exe una vez y deja un SQLite con:

- `funcs(start, end, ninstr, nrefs, ncalls)` — todas las funciones de `.pdata`.
- `calls(site_func, site, target, target_func)` — aristas directas (`call`/`jmp` con inmediato).
- `refs(site_func, site, target, kind, text)` — referencias rip-relative: `iat` (import),
  `str` (cadena en `.rdata`/`.data`) o `data`.
- `strings(va, text)`, `landmarks(va, name, note)`.

```
python tools/fl26dis.py --db %TEMP%\fl26dis.db --summary %TEMP%\fl26dis-summary.txt
```

Consultas que ya sirven para orientarse:

```sql
-- quien llama a una direccion
SELECT DISTINCT site_func FROM calls WHERE target = 0x1414f7e80;
-- funciones que usan VirtualAlloc
SELECT DISTINCT site_func FROM refs WHERE text LIKE '%VirtualAlloc%';
-- funciones que mencionan una cadena del menu
SELECT site_func, text FROM refs WHERE kind='str' AND text LIKE '%Conference%';
-- la funcion mas grande que referencia 'CompetitionRegulation'
SELECT f.start, f.end, f.ninstr FROM funcs f
  JOIN refs r ON r.site_func = f.start
 WHERE r.text LIKE '%CompetitionRegulation%' ORDER BY f.ninstr DESC LIMIT 5;
```

En el resumen (`--summary`) salen las 40 funciones más grandes, los nombres de los landmarks y
quién llama/referencia cada uno.

## 3. Las tres capas de datos

1. **Tablas en disco** (`common\etc\pesdb`, comprimidas WESYS): `Competition` (36 B),
   `CompetitionEntry` (12 B), `CompetitionRegulation` (2352 B), `Team` (1532 B), jugadores,
   entrenadores, países. Las lee `tools/pesdb.py`.
2. **Copias vivas**: el motor las carga en el heap. Las filas de entrada se ven como
   `[equipo u32][rowid u32][cid bajo u8][plaza u8][? u8][cid alto u8]`, ordenadas por la clave
   `cid << 6 | (plaza - 1)` (por eso `pack = true` en `fl26cid16`).
3. **Bloque de edición**: `0x143705e10` es el global del dueño; `[dueño + 0x48]` es el bloque.
   Dentro, las regulaciones tienen paso `0x314`, `id` u16 en `+0x00`, `cid` u32 en `+0x80` y la
   lista de clubs (handles `equipo << 14`) en `+0x170`, terminada en `0`/`0xffffffff`.
   **Ojo:** la base del array cambia de ejecución a ejecución (en la medida de hoy estaba en
   `0x7ff4e3997600`, no en `bloque + 0xc131b0`); no es una constante.

## 4. Los subsistemas, con direcciones

| dirección | nombre | qué hace |
|---|---|---|
| `0x1414b6a60` | `owner_getter` | devuelve el objeto dueño; `[+0x48]` = bloque |
| `0x1414bb000` | `reg_by_id` | regulación por **id** (el que usa el DLL) |
| `0x14158df30` | `comp_resolver` | resuelve competición por **id u16** (`cmp word [rax], di`) |
| `0x141eee1c0` | `reg_by_cid` | regulación por **cid** (contenedor de filas) |
| `0x141eee27c` | `reg_by_cid_read` | lee el cid de la fila (byte) — parche `reg` |
| `0x1414f1480` | `census` | censo de Select Team: arma competiciones y entradas |
| `0x1414f1500` | `census_cid_read` | cid de la fila de competición como **byte** — parche `cid` |
| `0x1414f1609` | `census_entry_pack` | clave de la entrada `cid << 6 | plaza-1` — parche `pack` |
| `0x1414f1d6a/e5a` | `census_key_a/b` | clave de 16 bits de la entrada — parche `map` |
| `0x1414f1d8b/ea1` | `census_find_a/b` | búsqueda por tabla plana — parche `map` |
| `0x1414f1576` | `census_insert` | inserta en el mapa (dedupe por byte) — parche `map` |
| `0x1414f7533` | `slot_list_build` | lista de slots de Select Team — parche `build` |
| `0x1414f7e80` | `reg_list_build` | **lista de clubs del registro** (`+0x170`) — parche `list` |
| `0x1414f7ec2` | | cid de la competición como **byte** (aquí se cruzan las ligas) |
| `0x1414f7f63` | | cid de cada entrada como **byte** (la comparación que mezcla) |
| `0x1419221f0` | `set_record_cid` | `mov [rcx+0x80], edx` (escribe el cid en el registro) |
| `0x1414cb030` | `slot_for_cid` | cid → plaza |
| `0x1414cb660` | `slot_walk` | recorre la tabla de plazas (paso `0x108`) y compara el cid del registro |
| `0x1414c9a10` / `0x1414c9740` | `list_add_club` / `list_clear` | añadir/quitar club de una lista |

Los avisos de `fl26swiss` ("list cleared by `1414f7ef0`", "clubs added by `1414f7f41`") son
**direcciones de retorno dentro de `0x1414f7e80`**, no funciones aparte.

## 5. Los menús (medido en pantalla)

- **Liga** (`Jugar > Liga > Nuevo`) lista toda competición con **fase de grupos o liga**. Por eso
  aparecen la Sudamericana (grupos=8), la Conference nuestra y también las del juego (UCL,
  Europa, Libertadores). Las copas de eliminatoria directa (Coppa Italia, `groups=0`) no salen.
  No depende de la fila de parámetros (probado) ni del slot.
- **Copa** (`Kick Off > Cup`) se sirve con `fl26swiss` + `fl26cupgrow` (vtable `0x142692d18`) y
  `fl26cupfree` (destructor `0x140c6b207`).
- **Select Team** (`Partido local`) usa los slots 0..122; `fl26clubs` responde los slots
  `SERVED` desde la regulación de cada liga (20 líneas servidas). El resto los llena el juego.

## 6. Los cuatro fallos abiertos y dónde viven

1. **Listas cruzadas** (Sudamericana 513←257, Yokary 359←615, NIFL 63←319, Danish 327←839):
   `0x1414f7ec2` y `0x1414f7f63` leen el cid como byte. Parche `ENABLE.list` en
   `fl26cid16.lua` (16 bits, con `r8d` para no romper `rcx` y REX obligatorio en `bpl`).
   **Pero el parche de la comparación no basta**: el bucle que *agrupa* las entradas antes de
   llamar a `0x1414f7e80` también corta por byte (toma como primera fila del grupo la primera
   con ese byte, p. ej. 257 en vez de 513), y es quien decide qué registro se rellena. Hay que
   parchear también ese agrupador; el índice (`calls` con `target = 0x1414f7e80`) da sus
   llamadores.
2. **Bélgica 1 equipo**: el DLL sirve 16 (slot 84 ← reg 111) pero el primer `count`/`get` llega
   antes de que la regulación esté cargada.
3. **Cierre `0x3fd2b2`** al liberar el buffer del menú de Copa (pool 2→0 y `cupgrow` no lo
   arreglan).
4. **Emblema de cids ≥ 256**: se sigue pidiendo por el byte bajo (`emb_<cid & 0xFF>`).

## 8. Cómo seguir

1. Consultar el SQLite por cadena/import para localizar el subsistema.
2. Confirmar la función con el grafo de llamadas (`calls`) y con `analyze_function` de REA si hace
   falta pseudocódigo.
3. Parchear en `sider/experimental/fl26cid16.lua` (o módulo nuevo) con **verificación de bytes**,
   cueva a <2 GB y A/B en vivo.
4. Documentar y commit local.

## 9. La cadena real del censo a la lista (medida 2026-11-06)

El builder **no se llama desde fuera**: no hay un solo `call`/`lea` en `.text` que apunte a
`0x1414f7e80` (barrido de `E8`, `E9` y `lea r64,[rip+disp]` = 0 aciertos). Se llega desde el
propio censo; la pila que deja `fl26swiss` lo confirma:

```
0x1414f7e80  (builder, limpia la lista y añade clubs)
  <- 0x1414f1ed3   dentro del censo 0x1414f1480
  <- 0x1414f6cb3
  <- 0x141b3779c
```

El bucle del censo:

```
0x1414f1dea  mov eax, [bloque + 0xd0bcf4]      ; nº de regulaciones
0x1414f1dfa  lea rcx, [bloque + 0xc12e9c]      ; array de regulaciones (base real medida)
0x1414f1e50  add rax, rax
0x1414f1e53  lea r14, [r12 + rax*8]            ; elemento de 16 B del vector
0x1414f1e57  mov rax, [r14]                    ; fila (equipo en +0, cid bajo en +8, alto en +0xb)
0x1414f1e5a  movzx ecx, byte [rax + 8]         ; SU CID, COMO BYTE  (parche map)
0x1414f1e77  movzx ecx, word [rax + 6]
0x1414f1e8b  call 0x1414edf60
0x1414f1ea1  call 0x1414ede90                  ; búsqueda (parche map)
0x1414f1ece  call 0x1414f7e80                  ; builder(ctx, &elemento, ...)
0x1414f1ed3  inc r13d
0x1414f1ed6  add rsi, 0x314                    ; siguiente regulación
```

Consecuencia: hay **dos** lecturas de byte que hay que ensanchar, no una:

1. la del censo en `0x1414f1e5a` (la que ya toca `map`), y
2. la comparación del builder en `0x1414f7f63` y el cid que escribe en el registro
   (`0x1414f7ec2` → `0x1419221f0`).

Si solo se arregla el builder, cada llamada filtra por el cid correcto pero el registro que se
rellena sigue siendo el que eligió el censo por byte. Por eso `ENABLE.list` a secas deja la
pantalla vacía o con el grupo equivocado: hay que decidir el `cid` en el censo (o sustituir su
clave por la de 16 bits de la entrada, que ya está en el vector como `[r14+8] = cid << 6 | plaza-1`).

## 10. Trampas de herramienta (para no repetirlas)

- Las entradas de `.pdata` son **RVA**, no VA: hay que sumar `0x140000000` (esto hacía que
  `pefunc.py` no encontrara ninguna función).
- `capstone.disasm()` **se para** en el primer byte que no decodifica; hay que reanudar byte a
  byte (lo hacen ya `fl26dis.py` y `disx.py`). Sin eso, un `.text` de 39 MB se queda en 13.000
  instrucciones.
- Hay una copia de la tabla `RUNTIME_FUNCTION` en `.data` (`0x1437d7f20`), con punteros de 32
  bits relativos; sirve para ver los límites de función de esa zona sin pasar por `.pdata`.
