# REA del nombre de las copas: donde se quedó (2026-11-06)

## Lo que se midió al abrir el menú (build con `block+0xc131b0`)

```
ctx=000000004D41F890 blk=00007FF4DF900010 n=65535
name scan: 14680054 bytes, 0 found
array starts 00007FF4DF900B3A off 0xb2a
567 record(s) with an id, first ones: 65535 43831 152 28589 ...
regcid -- 65535 regulations (scanning 1200), 22 ours seen, 22 got the full cid
Cup mode -- 270 world cup(s) added, all in (list 278 of 512)
```

Tres conclusiones:

1. **`[ctx+0x48]` no es el bloque del recuento.** Con el offset correcto (`+0xc131b0`) los ids
   siguen siendo basura (`65535 43831 152…`) y su cuenta en `+0xd0bcf4` es **65535**, cuando el
   recuento (`0x1414bc0a0`) escribe ahí un número pequeño (las regulaciones reales del mundo son
   ~692).
2. **`Kosovo Cup` no está en memoria**: 0 apariciones en 14,7 MB. Los nombres de regulación no se
   quedan en RAM como texto (se leen del fichero cuando la ficha los pide), así que anclar por
   nombre no sirve.
3. El registro del Mundial (id 34 / cid 27) **tampoco aparece** con el campo en `+0x80`: el bloque
   no es el bueno, o `+0x80` no es el cid en el array vivo.

## Lo que se está probando ahora (build 378.880 B, desplegada)

`regcid_fix` ya no adivina offsets: **localiza el bloque por sus cuentas**. El recuento deja
seguidos, en el mismo bloque:

```
+0xd0bce8  jugadores     (mundo: 101.500)
+0xd0bcec  equipos       (mundo: 3.547)
+0xd0bcf0  entrenadores
+0xd0bcf4  regulaciones  (mundo: ~692)
```

El DLL barre la memoria comprometida buscando el par (jugadores, equipos) con holgura
(90.000–120.000 y 3.000–4.200), deshace el offset (`blk = encontrado − 0xd0bce8`) y escribe en
`C:\Users\viarm\AppData\Local\Temp\opencode\regcid.txt`:

```
ctx=... hint=...
counts at <addr> -> blk <addr>
counts players=... teams=... coaches=... regs=...
first records (id/cid): id0/cid0 id1/cid1 ...
regs=... ours=... fixed=...
```

- Si `counts players=101500 teams=3547` → el bloque es el bueno.
- `first records` dice si `+0xc131b0` y `+0x80` son los campos correctos.
- `ours/fixed` dice si el mapa `reg → cid` casa y si se escribieron los cids completos.

## Si esto tampoco da ids válidos

Queda una vía: el array puede no estar en ese bloque sino en la **copia de modo** (la que
`fl26caps` realoja), y el `+0xd0bcf4` que vemos con 65535 puede ser el centinela de un bloque aún
sin contar. En ese caso, el siguiente paso es enganchar el **constructor del bloque**
(`0x1414b87dd`, `__ehvec_ctor(regs, 0x314, N)`) y quedarse con el puntero que recibe: ese es el
array, sin buscar.

### Blindaje (build 379.904 B)

1. Cuentas mas ajustadas a este mundo: jugadores **95.000-108.000**, equipos **3.300-3.800**.
2. Se descarta cualquier candidato con bloque negativo.
3. Se exige que el bloque y **doce registros del array** sean legibles (`VirtualQuery`, pagina
   comprometida y sin `PAGE_GUARD`).
4. Se exige que **6 de los 8 primeros registros** tengan id entre 1 y 1.200.
5. La escritura comprueba la legibilidad de cada registro antes de tocarlo.

Si encuentra bloque, `regcid.txt` dira `counts players=101500 teams=3547` y los primeros
`id/cid`. Si no encuentra nada, escribe `counts not found` y **no toca memoria**.

## 2026-11-06, tercera prueba: por que el juego dice "sin tamano de sorteo"

Sintoma: **entra** en Kick Off > Cup, pero al salir (o al entrar en una copa) se cierra con
`0x161efa600`, y la ficha dice que no hay tamano de sorteo.

Causa: el juego resuelve la copa por su **cid** (`phkind`, `0x14150af30`), que busca en el array
vivo el registro con `dword[+0x80] == cid`. Como ese campo solo lleva el byte bajo (o el array no
se encuentra), no hay registro: el juego cae a la **competicion 1** (FIFA Club World Cup), que no
tiene cuadro -> "sin tamano de sorteo" -> cierre al volver.

**No falta construir nada por copa**: el tamano de sorteo ya esta en la regulacion (`teams`, 2 en
las supercopas, 12/8 en Oceania/No FIFA, etc.). Lo que falta es que el juego **encuentre** esa
regulacion.

### Tercer metodo (build 378.880 B): firma conocida

El barrido por cuentas dio dos falsos positivos (90255/3112 y 107520/3360) y escribio en memoria
ajena. Ahora se busca el array por una **firma de datos** que no puede coincidir por azar:

```
reg 30 / cid 22   (Primera de Argentina)
reg 34 / cid 27   (Mundial)
reg 128 / cid 113 (Pro League Supercup)
reg 11 / cid 130  (Segunda argentina)
```

Se barre +-1 GB alrededor del bloque de `phkind` exigiendo `u16 id` y `u32 cid` en `+0x80`, que el
registro siguiente tenga un id plausible, y luego se camina hacia atras hasta la base. Solo
entonces se escribe. Si no aparece, escribe `no signature` y **no toca memoria**.

### Si tampoco aparece

El array no esta en el heap que vemos: habria que enganchar el **constructor del bloque**
(`0x1414b87dd`, `__ehvec_ctor(regs, 0x314, N)`) y quedarse con el puntero que recibe. Esa es la
ultima via, y no depende de buscar nada.

## 2026-11-06, cuarta prueba: **array encontrado** (y el cierre, explicado)

La busqueda por firma funciono:

```
ctx=000000004D4CE2B0 hint=00007FF4DF9A0010
signature reg 30/cid 22 at 00007FF4DA97CF44
array base 00007FF4DA977600
first records (id/cid): 1/1 2/2 3/2 4/2 5/3 6/3 7/4 8/5 9/5 10/5 11/130 12/1
ours=418 fixed=258
```

Dos lecturas de ahi:

1. **El array vivo empieza en la base encontrada** y `+0x80` es el cid: el registro de la
   regulacion 11 da **cid 130** (la Segunda de Argentina, que es su cid real), y el de la 30 da 22.
   La firma no era casualidad.
2. **`+0x00` no es el id de regulacion, es una clave ordenada**: los 10 bits bajos son el id y los
   altos un grupo de empate. Por eso la 12 (Supercopa de Albania, cid 257) sale como `12/1`: el
   cid esta truncado al byte (257 & 0xFF = 1), que es justo el fallo que arreglamos.

### El cierre de esta prueba fue nuestro

`regcid_fix` comparaba la **clave entera** contra el id del mapa. Para las regulaciones metidas en
grupos de empate (clave = id + grupo << 10) eso puede coincidir con el id de OTRA regulacion y
escribir su cid en un registro ajeno: corrupcion -> cierre al construir el menu.

### Correccion (build 378.880 B)

- El id se toma como **`clave & 0x3FF`**.
- Solo se escribe si el campo **aun lleva el byte truncado** (`cur == (want & 0xFF)`); si tiene
  otro valor, se deja y se cuenta como `skipped`. Asi no se puede tocar un registro que no sea
  nuestro ni uno ya arreglado.
- El log ahora imprime `id(grupo)/cid` y termina con `ours/fixed/skipped`.
- La corrupcion no persiste: el array vivo se reconstruye del fichero en cada arranque.

Con esto, si `fixed` sale alto y `skipped` bajo, el menu deberia resolver **nombre y tamano de
sorteo** de las 271 copas en la siguiente apertura.
