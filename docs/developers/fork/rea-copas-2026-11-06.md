# REA del nombre de las copas: donde se quedó (2026-11-06)

## Lo que se midió al abrir el menú (build con `block+0xc131b0`)

```
ctx=000000004D41F890 blk=00007FF4DF900010 n=65535
name scan: 14680054 bytes, 0 found
array starts 00007FF4DF900B3A off 0xb2a
567 record(s) with an id, first ones: 65535 43831 152 28589 ...
regcid -- 65535 regulations (scanning 1200), 22 ours seen, 22 got the full cid
Cup mode -- 270 world cup(s) added, all in (list 278 of 512)
```

Tres conclusiones:

1. **`[ctx+0x48]` no es el bloque del recuento.** Con el offset correcto (`+0xc131b0`) los ids
   siguen siendo basura (`65535 43831 152…`) y su cuenta en `+0xd0bcf4` es **65535**, cuando el
   recuento (`0x1414bc0a0`) escribe ahí un número pequeño (las regulaciones reales del mundo son
   ~692).
2. **`Kosovo Cup` no está en memoria**: 0 apariciones en 14,7 MB. Los nombres de regulación no se
   quedan en RAM como texto (se leen del fichero cuando la ficha los pide), así que anclar por
   nombre no sirve.
3. El registro del Mundial (id 34 / cid 27) **tampoco aparece** con el campo en `+0x80`: el bloque
   no es el bueno, o `+0x80` no es el cid en el array vivo.

## Lo que se está probando ahora (build 378.880 B, desplegada)

`regcid_fix` ya no adivina offsets: **localiza el bloque por sus cuentas**. El recuento deja
seguidos, en el mismo bloque:

```
+0xd0bce8  jugadores     (mundo: 101.500)
+0xd0bcec  equipos       (mundo: 3.547)
+0xd0bcf0  entrenadores
+0xd0bcf4  regulaciones  (mundo: ~692)
```

El DLL barre la memoria comprometida buscando el par (jugadores, equipos) con holgura
(90.000–120.000 y 3.000–4.200), deshace el offset (`blk = encontrado − 0xd0bce8`) y escribe en
`C:\Users\viarm\AppData\Local\Temp\opencode\regcid.txt`:

```
ctx=... hint=...
counts at <addr> -> blk <addr>
counts players=... teams=... coaches=... regs=...
first records (id/cid): id0/cid0 id1/cid1 ...
regs=... ours=... fixed=...
```

- Si `counts players=101500 teams=3547` → el bloque es el bueno.
- `first records` dice si `+0xc131b0` y `+0x80` son los campos correctos.
- `ours/fixed` dice si el mapa `reg → cid` casa y si se escribieron los cids completos.

## Si esto tampoco da ids válidos

Queda una vía: el array puede no estar en ese bloque sino en la **copia de modo** (la que
`fl26caps` realoja), y el `+0xd0bcf4` que vemos con 65535 puede ser el centinela de un bloque aún
sin contar. En ese caso, el siguiente paso es enganchar el **constructor del bloque**
(`0x1414b87dd`, `__ehvec_ctor(regs, 0x314, N)`) y quedarse con el puntero que recibe: ese es el
array, sin buscar.
